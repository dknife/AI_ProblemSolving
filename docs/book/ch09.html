CHAPTER 09

첫 번째 웹 서비스 만들기

이 장을 마치면
  • 한 페이지짜리 웹 도구의 구조를 설명할 수 있다.
  • 입력을 받아 결과를 보여 주는 화면을 만들 수 있다.
  • 입력에 따라 계산하고 반응하는 기능을 넣을 수 있다.
  • 표나 파일 형태의 자료를 다루게 만들 수 있다.
  • 남이 써도 헤매지 않도록 다듬을 수 있다.

이 장에서 만드는 것은 주소만 알면 누구나 열 수 있는 화면 한 장이다. 대단해 보이지 않지만, 지금까지 사람이 손으로 하던 계산과 확인을 이 한 장이 대신하기 시작하면 이야기가 달라진다.

만드는 과정은 한 번에 완성하는 것이 아니라 다섯 번에 나누어 키워 간다. 화면을 띄우고, 입력과 출력을 붙이고, 계산을 시키고, 자료를 다루고, 다듬는다. 매 단계마다 동작하는 상태를 유지하는 것이 중요하다 — 한꺼번에 만들어 놓고 안 되는 상태가 가장 고치기 어렵다.

9.1 한 페이지로 시작한다

8장에서 첫 결과물을 얻었다. 이 장에서는 그것을 명세서의 꼭 있어야 목록을 다 채우는 데까지 키운다. 그리고 그 과정을 다섯 단계로 나눠 진행한다.

이 장에서 만들 것

책의 예시는 6.5절의 명세서를 따른다. 완성되면 이런 모습이다.

완성 화면 -- 글로 그린 모습
==========================================================
  동아리 지출 기록

  이번 달 합계    1,247,000원
  간식 320,000 / 대관료 500,000 / 인쇄 127,000 / ...

  ---- 지출 추가 --------------------------------------
   날짜 [2026-03-04]   항목 [간식      v]
   금액 [        ]  결제 [카드 v]  이름 [      ]
                                        [ 추가 ]
  -----------------------------------------------------

  날짜    항목     금액       결제   이름
  3/07    대관료   500,000    이체   김OO
  3/04    간식      12,000    카드   이OO
  ...
                                  [ 표로 내보내기 ]

여러분은 자기 명세서의 화면을 만든다. 단계는 같다.

다섯 단계로 나눈다

표 9.1: 이 장의 진행 — 매 단계마다 동작하는 상태를 유지한다
절 무엇을 붙이나 끝나면 이것이 된다
9.1화면 뼈대열면 무언가 보인다
9.2입력과 목록입력한 것이 목록에 쌓인다
9.3계산과 반응합계가 자동으로 갱신된다

9.5다듬기남이 써도 헤매지 않는다

매 단계가 끝날 때마다 동작하는 상태여야 한다. 7.3절에서 말한 원칙이다. 그리고 매 단계 끝에 사본을 만든다(expense_v1.html, v2, …).

파일 하나를 지킨다

만들다 보면 인공지능이 파일을 나누자고 제안할 때가 있다. 코드가 길어졌으니 CSS를 별도 파일로 분리하겠습니다 같은 것이다. 거절한다.

파일을 나누지 말고 expense.html 하나로 유지해 줘. 나중에 그 파일 하나만 올려서 공개할 계획이다.

이유는 셋이다. 파일이 하나면 (1) 잃어버릴 일이 없고, (2) 남에게 보내기 쉽고, (3) 10장의 배포가 가장 간단해진다. 코드가 천 줄이 넘어가면 나누는 것이 낫지만, 우리가 만드는 크기에서는 하나가 낫다.

시작 상태 확인

8장에서 받은 파일을 열고 지금 무엇이 되는지 표시해 보자.

현재 상태 점검
[  ] 페이지가 열린다
[  ] 입력 칸이 보인다
[  ] 무언가 입력할 수 있다
[  ] [추가]를 누르면 목록에 쌓인다
[  ] 합계가 나온다
[  ] 새로고침해도 남아 있다
[  ] 파일로 내보낼 수 있다
[  ] 휴대전화에서 열린다

8장을 마쳤다면 위에서 서너 개가 이미 되어 있을 것이다. 이 장은 나머지를 채우는 과정이다.

요점

이미 되는 것을 망가뜨리지 않는 것이 새 기능을 붙이는 것만큼 중요하다. 그래서 매번 요청 끝에 나머지는 그대로 둬를 붙이고, 매 단계 끝에 사본을 남긴다.

예시가 자기 문제와 다를 때

이 책의 예시는 지출 기록이다. 여러분의 것은 다를 것이다. 실습 일정일 수도, 조별 과제 진행 상황일 수도, 봉사 시간 집계일 수도 있다.

걱정하지 않아도 된다. 구조는 거의 같다.

표 9.2: 다른 문제, 같은 구조
만드는 것 입력 목록 집계
지출 기록지출 한 건지출 목록항목별 합계
실습 일정일정 한 건일정 목록다가오는 것
조별 과제할 일 한 건할 일 목록진행률
봉사 시간활동 한 건활동 목록기관별 시간
독서 기록책 한 권읽은 목록월별 권수

한 건을 입력하고, 목록으로 쌓고, 무언가를 집계한다. 이 구조가 이 수업에서 만드는 것의 대부분을 덮는다. 그래서 이 장을 따라가면서 지출을 자기 것으로 바꿔 읽으면 된다.

9.2 입력과 출력 만들기

첫 단계는 한 건을 입력하면 목록에 쌓이는 것이다. 이것만 되면 절반은 끝난 셈이다. 나머지는 여기에 얹는다.

입력 칸의 종류를 정한다

무엇을 어떤 방식으로 받을지 미리 정해야 한다. 이것을 정하지 않고 입력 칸을 만들어 줘라고 하면 전부 글자 입력으로 나온다.

표 9.3: 입력 칸의 종류
무엇을 어떤 칸으로 왜
날짜날짜 고르기형식이 저절로 맞는다
금액숫자 전용휴대전화에서 숫자 자판이 뜬다
항목고르기 + 직접 입력표기가 통일되면서 예외도 받는다
결제수단고르기셋뿐이다
이름글자
메모여러 줄 글자길어질 수 있다

고르기로 만들 수 있는 것은 고르기로 만든다. 5.4절에서 본 표기 불일치 문제(카드/신용카드/체크)가 애초에 생기지 않기 때문이다. 이것 하나로 11장의 자료 정리 작업이 크게 줄어든다.

프롬프트 9.1: 입력 칸과 목록 만들기

금액과 이름 칸만 비워진다는 요청을 눈여겨보자. 이런 것은 실제로 써 보지 않으면 생각나지 않는데, 6.4절에서 종이로 시험해 본 사람은 알게 된다. 같은 날 여러 건을 연속으로 넣을 때 날짜를 매번 다시 고르는 것은 짜증나는 일이다.

결과를 확인하는 방법

받은 뒤 다음을 순서대로 해 본다. 되는 것만 확인하지 말고 안 되는 경우도 해 본다.

  • 정상 입력 — 다섯 칸을 다 채우고 추가
  • 연속 입력 — 바로 이어서 하나 더 추가 (날짜가 남아 있는가?)
  • 빈 칸 — 금액을 비우고 추가 (어떻게 되는가?)
  • 이상한 값 — 금액에 음수, 아주 큰 수
  • 새로고침 — 지금은 사라질 것이다 (9.4절에서 해결)

3–4번에서 이상하게 동작해도 지금은 넘어간다. 9.5절에서 다룬다. 다만 무엇이 이상한지 적어 둔다.

코드에서 확인할 곳

돌아온 코드에서 두 곳을 찾아보자. 이 두 곳은 앞으로 자주 고치게 된다.

첫째, 고르기 목록.

<select id="category">
  <option>간식</option>
  <option>대관료</option>
  <option>인쇄비</option>
  <option>교통비</option>
  <option>물품</option>
  <option>기타</option>
</select>

항목을 바꾸고 싶으면 여기서 글자만 고치면 된다. 줄을 통째로 지우거나 복사해 더할 수도 있다. 여러분이 직접 고칠 수 있는 자리다.

둘째, 목록에 더하는 부분.

function addExpense() {
  const item = {
    date: document.getElementById('date').value,
    category: document.getElementById('category').value,
    amount: Number(document.getElementById('amount').value),
    payment: document.getElementById('payment').value,
    name: document.getElementById('name').value
  };
  expenses.push(item);   // 목록에 더한다
  render();              // 화면을 다시 그린다
}

문법은 몰라도 된다. 다섯 개의 값을 모아 한 건으로 만들고, 목록에 넣고, 화면을 다시 그린다는 흐름만 보이면 충분하다. 나중에 항목을 하나 더 추가하고 싶어지면 여기에도 한 줄이 늘어나야 한다는 것을 알게 된다.

요점

코드에서 자기가 정한 이름(date, category, amount…)이 반복해 나타나는 것을 확인하자. 이 이름들이 5.4절에서 정한 열 이름과 같아야 나중에 자료를 주고받을 때 헷갈리지 않는다.

이 단계에서 흔한 문제

추가는 되는데 화면이 안 바뀐다. 목록에는 들어갔는데 다시 그리지 않은 것이다. 추가한 뒤 화면을 다시 그려 줘라고 요청한다.

같은 것이 계속 쌓인다. 입력 칸이 안 비워져서 실수로 두 번 눌린 경우다.

한글이 깨진다. 파일 저장 방식의 문제다. 파일을 UTF-8로 저장했는데 한글이 깨진다고 알려 주면 고쳐 준다.

휴대전화에서 표가 잘린다. 9.5절에서 다룬다. 지금은 컴퓨터에서만 확인해도 된다.

9.3 계산하고 반응하게 하기

목록이 쌓이면 이제 그것으로 무언가를 계산한다. 이 절의 진짜 주제는 계산이 아니라 계산 규칙을 말로 정확히 적는 연습이다.

규칙을 문장으로 먼저 적는다

프롬프트를 쓰기 전에 종이에 규칙을 적는다. 이 단계를 건너뛰면 반드시 다시 하게 된다.

합계를 보여 줘

이 지시로는 다음이 정해지지 않는다.

  • 전체 합계인가, 이번 달 합계인가?
  • 이번 달의 기준은 무엇인가 — 달력의 달인가, 지난 정산 이후인가?
  • 항목별 합계도 필요한가?
  • 0원인 항목도 보여 주는가?
  • 원 단위 표시는? 쉼표는?

정해 놓고 적으면 이렇게 된다.

목록에 있는 모든 지출의 금액을 더해 전체 합계를 낸다. 세 자리마다 쉼표를 넣고 끝에 원을 붙인다. 항목별로도 합계를 내되, 금액이 0인 항목은 표시하지 않는다. 금액이 큰 항목부터 보여 준다.

요점

말로 애매한 것은 화면에서도 애매하게 나온다. 계산 규칙을 문장으로 적을 수 없다면, 그것은 아직 결정하지 않은 것이다. 인공지능이 대신 결정해 줄 수는 있지만, 그 결정이 맞는지는 여러분만 안다.

프롬프트 9.2: 합계 계산 붙이기

반드시 검산한다

계산이 붙으면 손으로 확인한다. 이것을 건너뛰는 학생이 많고, 나중에 발표에서 문제가 된다.

  1. 지출 세 건을 넣는다. 값은 계산하기 쉬운 것으로 (10000, 20000, 30000)
  2. 합계가 60,000원으로 나오는가?
  3. 항목을 서로 다르게 해서 세 건 더 넣는다. 항목별 합계가 맞는가?
  4. 한 건을 삭제한다. 합계가 그만큼 줄었는가?
  5. 0원짜리를 넣어 본다. 어떻게 되는가?
주의

동작한다고 맞는 것이 아니다. 합계 자리에 숫자가 나오는 것과 그 숫자가 맞는 것은 다른 문제다. 계산이 틀려도 오류 메시지는 뜨지 않는다. 12.4절에서 다시 다루지만, 습관은 지금 들여야 한다.

계산 부분 찾아보기

function updateTotal() {
  // 전체 합계
  const total = expenses.reduce((sum, e) => sum + e.amount, 0);
  document.getElementById('total').textContent =
    total.toLocaleString() + '원';

  // 항목별 합계
  const byCategory = {};
  for (const e of expenses) {
    byCategory[e.category] = (byCategory[e.category] || 0) + e.amount;
  }
  // ... 큰 것부터 정렬해 화면에 표시 ...
}

세 곳만 알아보면 된다.

  • sum + e.amount — 더한다. 만약 평균을 내고 싶다면 이 근처가 바뀐다
  • toLocaleString() — 쉼표를 넣는다
  • '원' — 화면에 붙는 글자. 다른 단위로 바꾸고 싶으면 여기

여유가 있다면 반대 방향도 만들 수 있다. 이전에 내보낸 파일을 다시 올려 이어서 쓰는 것이다.

내보낸 CSV 파일을 다시 올려 목록을 복원하는 기능을 넣어 줘. [파일 불러오기] 단추를 누르면 파일을 고를 수 있고, 고른 파일의 내용이 현재 목록에 더해진다. 이미 있는 것과 똑같은 건(날짜·항목·금액·이름이 모두 같은 것)은 건너뛰고, 몇 건을 불러왔고 몇 건을 건너뛰었는지 알려 줘.

덮어쓴다가 아니라 더한다로 정한 것과, 중복을 건너뛰게 한 것을 눈여겨보자. 덮어쓰기는 되돌릴 수 없고, 되돌릴 수 없는 동작은 사고를 만든다(3.4절).

9.5 쓰기 쉽게 다듬기

기능은 다 들어갔다. 이제 남이 써도 헤매지 않게 만든다. 기준은 예쁘게가 아니라 헤매지 않게다.

남에게 시켜 보면 안다

6.4절에서 종이로 했던 것을 이번에는 실제 화면으로 한다.

  1. 아무 설명 없이 지출 하나를 넣어 보세요라고 한다
  2. 옆에서 지켜본다. 도와주지 않는다
  3. 멈칫하는 지점, 잘못 누르는 지점, 다시 확인하는 지점을 적는다
  4. 끝나면 어디가 헷갈렸는지 묻는다

세 명이면 고칠 것 서넛이 나온다. 그리고 두 사람 이상이 같은 곳에서 막혔다면 반드시 고친다. 한 명만 막힌 것은 그 사람의 습관일 수 있다.

프롬프트 9.5: 쓰기 쉽게 다듬기

프롬프트가 무엇이 문제였고 그래서 무엇을 해 달라는 짝으로 되어 있는 것을 보자. 7.3절의 어디가·왜·어떻게가 여섯 번 반복된 모양이다.

눈에 잘 보이게

교양 수업이므로 디자인을 깊이 다루지 않는다. 다만 다음 넷만 지켜도 크게 나아진다.

  • 중요한 것을 크게. 합계가 가장 크고, 목록이 그다음, 안내가 가장 작다
  • 색은 두세 가지만. 강조할 곳에만 색을 쓰고 나머지는 회색 계열
  • 여백을 준다. 빽빽한 것보다 낫다
  • 같은 것은 같게. 단추 모양이 자리마다 다르면 헷갈린다

누구나 쓸 수 있게

마지막으로 짚어 둘 것이 있다. 만든 것을 누가 못 쓰게 되는지 생각해 보는 일이다.

  • 글자가 작거나 색 대비가 낮으면 — 눈이 불편한 사람이 못 쓴다
  • 색으로만 구분하면 — 색을 구분하기 어려운 사람이 못 쓴다 (붉은 글씨 옆에 표시도 함께)
  • 마우스로만 되면 — 키보드만 쓰는 사람이 못 쓴다 (탭 키로 이동되는지 확인)
  • 안내가 없으면 — 처음 보는 사람이 못 쓴다
화면의 색 대비를 확인해서, 회색 글씨가 배경과 충분히 구분되게 해 줘. 그리고 붉은 글씨로만 알려 주는 안내에는 표시(!)도 함께 붙여 줘. 탭 키만으로 모든 칸과 단추를 순서대로 이동할 수 있는지도 확인해 줘.
요점

나는 잘 보이는데는 기준이 아니다. 만든 사람은 어디에 무엇이 있는지 이미 알고 있기 때문에 언제나 잘 쓴다. 처음 보는 사람이 헤매지 않는가만이 기준이다.

여기서 멈춘다

다듬기는 끝이 없다. 4.4절에서 정한 성공 기준으로 돌아가 확인하고, 만족했으면 멈춘다.

  • 명세서의 꼭 있어야 다섯 개가 모두 되는가
  • 세 사람이 설명 없이 쓸 수 있는가
  • 실제 자료를 넣고 끝까지 해 봤는가
  • 계산 결과를 손으로 검산했는가
  • 사본(expense_v5.html 등)을 남겼는가

다섯 개가 다 되면 10장으로 간다. 남은 것은 있으면 좋음 칸으로 옮기고, 배포한 뒤 반응을 보고 결정한다.

실습 9-5. 저장과 내보내기

9.4절의 두 프롬프트로 저장과 내보내기를 붙인다. 그리고 확인한다.

  • 새로고침해도 목록이 남아 있다
  • 창을 닫았다 열어도 남아 있다
  • 내보낸 파일이 엑셀에서 한글 깨짐 없이 열린다
  • 열이 제대로 나뉘어 있고 금액이 숫자로 인식된다
  • 화면의 건수와 파일의 행 수가 같다

실습 9-8. 다듬고 마무리

관찰에서 나온 것을 9.5절의 형식(무엇이 문제였고 그래서 무엇을 해 달라)으로 정리해 한 번에 요청한다. 그리고 마지막 점검표를 확인한다.

  • 명세서의 꼭 있어야가 모두 된다
  • 세 사람이 설명 없이 쓸 수 있다
  • 실제 자료로 끝까지 해 봤다
  • 검산했다
  • 사본을 남겼다
  • 글자 크기·색 대비를 확인했다

9장 요약
  • 한 번에 만들지 않고 다섯 단계로 나눠 키운다. 화면 뼈대 → 입력과 목록 → 계산 → 자료 → 다듬기. 매 단계마다 동작하는 상태를 유지하고 사본을 남긴다.
  • 파일은 하나로 유지한다. 인공지능이 나누자고 제안해도 거절한다 — 잃어버릴 일이 없고, 보내기 쉽고, 10장의 배포가 가장 간단해진다.
  • 이 수업에서 만드는 것의 대부분은 한 건을 입력하고, 목록으로 쌓고, 무언가를 집계하는 같은 구조다. 지출이든 일정이든 봉사 시간이든 마찬가지다.
  • 고르기로 만들 수 있는 것은 고르기로 만든다. 표기 불일치(카드/신용카드/체크)가 애초에 생기지 않아 11장의 자료 정리가 크게 줄어든다.
  • 확인할 때는 되는 경우만 보지 말고 빈 칸, 이상한 값, 연속 입력도 해 본다. 지금 고치지 않더라도 무엇이 이상한지 적어 둔다.
  • 계산은 규칙을 문장으로 먼저 적고 시작한다. 말로 애매한 것은 화면에서도 애매하게 나온다. 조건이 여러 개면 표로 적어 그대로 프롬프트에 붙인다.
  • 동작한다고 맞는 것이 아니다. 합계 자리에 숫자가 나오는 것과 그 숫자가 맞는 것은 다르고, 계산이 틀려도 오류는 뜨지 않는다. 반드시 손으로 검산한다.
  • 저장은 브라우저 저장과 파일 내보내기를 함께 쓴다. 브라우저 저장은 그 기기에만 남고 공유되지 않으므로, 그 사실을 화면에서 사용자에게 알린다.
  • 저장된 자료가 깨졌을 때 어떻게 할지 미리 정해 둔다. 정하지 않으면 어느 날 페이지가 통째로 안 열린다.
  • 자료를 다루는 기능에서는 언제나 되돌릴 수 있는 쪽을 고른다. 더하기는 지우면 되지만 덮어쓰기는 되돌릴 수 없다.
  • 실제 자료를 15건 이상 넣어 본다. 가짜 자료 세 건으로는 드러나지 않는 문제가 있다.
  • 다듬기의 기준은 예쁘게가 아니라 헤매지 않게다. 세 사람에게 설명 없이 시켜 보고, 둘 이상이 막힌 곳은 반드시 고친다.
  • 나는 잘 보이는데는 기준이 아니다. 글자 크기, 색 대비, 색으로만 하는 구분, 키보드 이동을 확인한다.
  • 다듬기는 끝이 없으므로 성공 기준으로 돌아가 멈춘다. 남은 것은 있으면 좋음으로 옮기고 배포 후 반응을 보고 결정한다.
9장 연습문제
  1. ★ 이 장에서 매 단계마다 동작하는 상태를 유지하라고 하는 이유를 설명하시오.
  2. ★ 다음 입력 항목에 대해 어떤 종류의 입력 칸이 적절한지 고르고 이유를 쓰시오(표 9.3 참조).
    1. 실습 기관 이름 (전체 12곳으로 정해져 있음)
    2. 봉사 시간 (숫자, 소수점 가능)
    3. 활동 소감 (두세 문장)
    4. 참여 여부 (예/아니오)
  3. ★ 합계를 보여 줘라는 지시로 정해지지 않는 것을 다섯 가지 이상 나열하시오.
  4. ★★ 다음 계산 규칙을 9.3절처럼 조건 표로 정리하시오.

    봉사 시간을 기관별로 합산하되, 8시간을 넘는 하루 기록은 8시간으로 계산한다. 인증서가 없는 활동은 합계에서 빼되 목록에는 표시한다. 같은 날 같은 기관에 두 건이 있으면 합쳐서 계산한다.

  5. ★★ 표 9.4의 세 가지 저장 방법 중 브라우저 저장을 골랐을 때, 사용자에게 반드시 알려야 할 것이 무엇이고 왜 그런지 설명하시오. 그리고 그 한계 때문에 생길 수 있는 실제 상황을 하나 예로 드시오.
  6. ★★ 9.4절에서 자료 불러오기를 덮어쓰기가 아니라 더하기로 만든 이유를 3.4절의 원칙과 연결해 설명하시오.
  7. ★★★ 자기 결과물을 세 사람에게 설명 없이 써 보게 하고, 관찰 기록을 제출하시오. 보고에는 (1) 세 사람의 관찰 기록, (2) 둘 이상이 막힌 지점, (3) 그것을 고치기 위해 쓴 프롬프트, (4) 고치기 전후 화면, (5) 고친 뒤 다시 시켜 본 결과가 포함되어야 한다.
  8. ★★★ 실제 자료 30건 이상을 넣고, 다음을 확인해 보고하시오. (1) 실제 자료에서만 나타난 문제 세 가지, (2) 그중 자료 형태(5.4절) 때문에 생긴 것과 프로그램 때문에 생긴 것의 구분, (3) 각각을 어떻게 해결했는지, (4) 해결하지 않고 있으면 좋음으로 미룬 것과 그 판단 근거.
