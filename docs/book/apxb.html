APPENDIX B

문제 해결 프롬프트 사전

본문에서 쓴 프롬프트를 목적별로 모았다. 그대로 복사해 쓰되, 자리에는 자기 문제의 내용을 채워야 한다. 빈 채로 보내면 그럴듯하지만 자기 문제와 무관한 답이 돌아온다.

문제를 정의할 때 (4장)

불편을 구체화하기

나는  상황에서  일을 반복하고 있다.
이 불편을 확인 가능한 문제로 다듬으려 한다. 다음을 물어봐 줘. 한 번에 하나씩, 내 답을 듣고 다음 질문으로 넘어가 줘.
- 얼마나 자주 일어나는가

- 한 번에 얼마나 걸리거나 어떤 대가를 치르는가

- 누가 겪는가

- 그래서 무엇이 나빠지는가
내 답이 여전히 모호하면 다시 물어 줘.

이해관계자 찾기

아래 문제에 관련된 사람들을 찾아 줘.
- 겪는 사람 / 시키는 사람 / 결과를 받는 사람으로 나눠 줘

- 각자가 무엇을 얻고 싶어 하고 지금 무엇을 잃고 있는지

- 이 문제가 해결되면 오히려 곤란해지는 사람이 있다면 알려 줘

문제 진술문 반박받기

아래는 내가 쓴 문제 진술문이다.
너는 이것을 심사하는 까다로운 심사위원이다. 칭찬하지 말고 다음만 지적해 줘.
1. 근거 없이 단정한 부분

2. 확인되지 않은 가정

3. 이 문제가 사실은 다른 문제의 증상일 가능성

4. 이 문제를 겪지 않는 사람이 읽으면 이해가 안 될 부분
각 지적에 무엇을 확인하면 되는지를 한 줄로 붙여 줘.

이미 있는 해법 찾기

이런 문제를 다루는 도구나 방법이 이미 있는지 알려 줘. 있다면 그것으로 충분한지, 부족하다면 무엇이 부족한지도. 없으면 없다고 해도 된다. 확실하지 않은 것은 [확인 필요]로 표시해 줘.

문제를 쪼갤 때 (5장)

여러 축으로 나누기

아래 문제를 서로 다른 세 가지 축으로 각각 나눠 줘.
각 축마다: 3–4개 가지로, 겹치지 않게, 기타는 만들지 말고, 그 축으로 나눴을 때 어떤 해법이 보이는지 한 줄 덧붙여 줘.

내 트리 점검받기

아래는 내가 그린 로직 트리다(들여쓰기로 계층 표시).
다음을 지적해 줘. 잘한 점은 말하지 않아도 된다.
1. 겹치는 가지  —  어느 것과 어느 것이 왜

2. 빠진 가지  —  이 분류에서 다뤄지지 않는 경우

3. 층위가 맞지 않는 가지

4. 원인이 아니라 해법이 들어와 있는 가지

사실과 추측 구분하기

방금 만든 트리에서 각 가지가 사실로 확인된 것인지 추측인지 표시해 줘. 추측이라면 무엇을 보면 확인할 수 있는지도. 내가 준 자료에 없는 내용은 전부 추측으로 표시해야 한다.

해법을 찾고 고를 때 (6장)

대안 늘리기

아래 문제의 이 부분을 다룰 방법을 12가지 제안해 줘.
- 서로 확실히 다른 방법일 것 (세부만 다른 것은 하나로)

- 다음이 각각 최소 둘씩: 없애기 / 줄이기 / 옮기기 / 자동화 / 쉽게 하기

- 만들지 않는 해법(규칙 변경, 이미 있는 것 사용)을 최소 셋

- 각각 한 문장으로만, 평가는 하지 말 것
어느 것이 좋은지는 말하지 마. 내가 정한다.

빠뜨린 기준 찾기

아래는 내가 고려 중인 해법 넷과 비교 기준 넷이다.
1. 내가 빠뜨린 중요한 기준이 있는가

2. 각 대안에서 내가 과소평가하고 있을 위험은

3. 이 중 어느 것도 좋지 않다면 그 이유는
어느 것을 고르라고 추천하지는 마. 판단 재료만 달라.

범위 줄이기 압박

아래 기능 목록을 한 사람이 4주 안에 만들 수 있는 크기로 줄여 줘.
- 꼭 있어야는 다섯 개 이하

- 꼭만으로 일이 처음부터 끝까지 되어야 함

- 나머지는 이번엔 안 함으로 옮기고 왜 미뤄도 되는지 한 줄씩

만들 때 (8–11장)

제작 프롬프트 서식

[만들 것] 을 만들어 줘. 파일 하나로만, 외부 라이브러리 없이 동작해야 해.
[누가 쓰나] 
[화면과 흐름] 
[기능  —  이것만] 1) 2) 3) 4) 5)
[자료 형식] 열 이름과 각각의 형식
[이번엔 넣지 말 것] . 요청하지 않은 기능을 넣지 말 것.
[지켜야 할 것] (확인할 수 있는 조건으로)
[만든 뒤] 1) 어디에 저장하고 어떻게 여는지 2) 내가 고칠 만한 부분이 어디인지 3) 네가 임의로 정한 것

프롬프트 미리 점검받기

아래는 내가 요청하려는 프롬프트다. 아직 만들지 말고 이것만 검토해 줘.
1. 내가 지정하지 않아서 네가 임의로 정하게 될 것들을 모두

2. 서로 모순되거나 애매한 지시

3. 이대로 만들면 내가 실망할 가능성이 높은 부분

수정 요청

 부분에서,  때문에  하다.
 하게 바꿔 줘. 나머지는 그대로 둬.

코드 읽기

아래는 내가 만든 것의 일부다.
프로그래밍을 배우지 않은 사람이 이해할 수 있게 알려 줘.
1. 이 부분이 하는 일을 한 문장으로

2. 지우면 화면에서 무엇이 사라지는지

3. 내가 바꿔도 안전한 곳과 건드리면 안 되는 곳
문법을 설명하지 말고 무슨 일을 하는지만.

자료 처리 요청

[자료]  파일. 열은 . 각 행이  한 건. 약 행.
[할 일] 
[확인] 처리한 행 수, 이상한 값이 있는 행 수, 결과에 들어간 행 수를 함께 출력해 줘.
[제약] 원본 파일은 고치지 말고 새 파일로. 버린 행은 따로 저장. 설치가 필요한 것은 쓰지 말 것.

고칠 때 (12장)

오류 보고

[하려던 것] 
[한 것] 
[나온 것] (화면에 뜬 것을 그대로 붙여 넣는다)
[해 본 것] 
[언제부터]  한 뒤부터 이렇게 됐다.

원인 먼저 듣기

바로 고치지 말고 먼저 알려 줘.
1. 무엇이 원인인지 프로그래밍을 모르는 사람이 이해할 수 있게

2. 왜 어제까지는 되다가 지금 안 되게 됐는지

3. 고치는 방법이 둘 이상이면 각각의 장단점
설명을 듣고 어떻게 할지 내가 정한다.

숨은 가정 드러내기

방금 만든 계산에 대해 알려 줘.
1. 내가 지정하지 않아서 네가 정한 처리 방식을 모두 (빈칸 처리, 경계 포함 여부, 반올림 시점, 정렬 기준, 중복 판정 등)

2. 각각에 대해 다른 선택도 가능했는지, 다르게 하면 결과가 어떻게 달라지는지

3. 이 중 내가 확인해야 할 것
코드는 고치지 말고 설명만.

확인 목록 만들기

아래는 내가 만든 것의 기능 목록과 성공 기준이다.
확인할 시험 항목을 만들어 줘.
- 각 항목은 무엇을 하면 / 무엇이 나와야 두 칸으로

- 각 기능마다 정상 / 이상한 값 / 비어 있음 세 경우를 모두

- 눈으로 판정할 수 있게 구체적으로 (잘 동작한다 금지)

- 15개 이하, 표로

검증할 때 (전 장)

방금 답한 내용 중 각 주장이 어디에서 나온 것인지 표시해 줘. 내가 준 자료 / 검색한 것(출처 주소) / 원래 알고 있던 것으로 구분해 줘.
네 결론에 반대하는 입장에서 가장 강한 반박을 세 가지 해 봐. 그리고 그 반박이 타당한지 평가해 줘.
각 항목의 확신 정도를 [높음/보통/낮음]으로 표시해 줘. 낮음인 것은 무엇을 확인하면 되는지도.
같은 문제를 완전히 다른 방법으로 다시 풀어 봐. 두 결과가 같은지 비교하고, 다르면 어느 쪽이 맞을지 판단해 줘.
정리 전 건수와 정리 후 건수를 각각 알려 줘. 다르다면 어느 건이 왜 빠졌는지 전부 보여 줘.

맥락을 옮길 때 (2.4절)

지금까지의 대화를 새 대화창에 옮겨 이어 가려 한다. 다음을 정리해 줘.
1. 지금 하려는 일과 목표

2. 지금까지 내린 결정과 그 이유

3. 시도했지만 안 된 방법과 그 이유

4. 현재 상태와 다음에 할 일
새 대화에 그대로 붙여 넣을 수 있게, 설명 없이 정리된 내용만.

쓰지 말아야 할 프롬프트

알아서 잘 만들어 줘.

무엇을 만들지 정하지 않은 것이다. 인공지능이 정하게 되고, 그 결정이 내 문제와 맞을 확률은 낮다.

이 자료 분석해서 결론 내려 줘. (실제 명단·연락처가 든 파일 첨부)

개인정보를 그대로 올린 것이다. 이름을 바꾸거나 일부만 올린다(7.2절).

로그인, 게시판, 알림, 통계, 관리자 페이지까지 다 만들어 줘.

한 번에 너무 많다. 하나씩 붙이고 매 단계 동작을 확인한다(7.3절).

정말이야? 확실해?

맞는 답까지 철회하게 만든다. 어떻게 확인할 수 있어?라고 묻는다(7.4절).

안 되는데 고쳐 줘.

무엇이 어떻게 안 되는지가 없다. 네 요소를 갖춰 적는다(12.2절).
